# Task 5.4 — Baseline MCP server: generic UI automation for the chess demo

Read first: `demos/chess/src/a11y.rs` (the `a11y tree|click|type` commands the app serves over
IPC), `crates/rust-use-agent/src/ipc` (Client, Endpoint), `crates/rust-use-agent/src/mcp.rs`
(how our own MCP shim uses rmcp 3.12 — follow the same patterns). **Do NOT run `git commit`.**

Create `demos/chess-mcp-baseline` (package `chess-mcp-baseline`, `publish = false`), a stdio MCP
server representing how an agent drives a desktop app TODAY without rust-use: through a generic
automation layer that exposes the element tree and lets it click elements. It must look and
behave like typical accessibility/browser automation MCP servers. Nothing chess-specific in the
tool design.

Tools (descriptions short, neutral, ≤ 600 chars combined — same budget as ours, for fairness):
- `get_ui_tree {}` → the app's `a11y tree` JSON as text content.
- `click { element_id: string }` → `a11y click <id>` reply as text.
- `type_text { text: string }` → `a11y type <text>` reply.
Server info: name `ui-automation`, instructions: "Inspect the UI with get_ui_tree, then interact
with click and type_text."

CLI: `chess-mcp-baseline [--app chess]` (default app `chess`). Connection errors → MCP tool
error result with a clear message, not a crash.

Test: in-process rmcp client over a duplex pipe against a server whose endpoint is a stub
`Fn(&str) -> String` (factor the IPC client behind a small trait so it can be stubbed) — list tools,
call each.

Acceptance: full gate passes.
